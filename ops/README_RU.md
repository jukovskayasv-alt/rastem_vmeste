# Подготовка существующей VM для deploy

Этот скрипт предназначен только для владельца уже существующей VM с **Ubuntu 24.04 x64**. Он не создаёт VM, сеть, аккаунты или другие облачные ресурсы. Запуск выполняется вручную один раз. В репозитории нет утверждения, что сервер или GitHub runner уже подключены.

## Как открыть правильный терминал с Android

Используйте SSH или Cloud Shell, уже авторизованный на VM. Обычное приглашение командной строки заканчивается символом `$`, например:

```text
owner@server:~$
```

Строка `login:` в Serial Console означает, что консоль ждёт имя локального пользователя VM. Команды ниже туда вводить нельзя, пока вход не выполнен и не появилось приглашение `$`.

## Что подготовить

1. Откройте существующий `jukovskayasv-alt/rastem_vmeste` и сначала смените его видимость с Public на **Private**: **Settings → General → Danger Zone → Change repository visibility**. Не устанавливайте runner, пока репозиторий публичный.
2. Создайте временный токен регистрации: **Settings → Actions → Runners → New self-hosted runner → Linux → x64**. Токен короткоживущий; это не токен Telegram и не постоянный секрет приложения.
3. После появления ветки `skif` на GitHub получите на VM именно её и перейдите в корень приложения:

   ```bash
   git clone --branch skif --single-branch https://github.com/jukovskayasv-alt/rastem_vmeste.git skif
   cd skif
   ```

   Команду клонирования выполняйте в уже авторизованной на GitHub среде; не добавляйте токен в URL, сообщение или историю shell. Если репозиторий уже клонирован, используйте `git fetch origin skif`, затем `git switch skif` и `git pull --ff-only origin skif`. В браузере можно выбрать ветку `skif`, затем **Code → Download ZIP**, распаковать архив и открыть его корень. Не используйте содержимое `main`: существующая ветка и сайт не меняются.
4. Убедитесь, что `/opt/actions-runner` не содержит старую установку. Скрипт специально откажется заменять существующий runner или регистрацию. Не удаляйте эти данные вслепую: сначала разберитесь, какой runner уже работает.

## Единственная команда установки

Из корня репозитория явно запустите:

```bash
sudo python3 ops/bootstrap_host.py --repository jukovskayasv-alt/rastem_vmeste
```

Скрипт до изменения хоста проверяет root, Ubuntu 24.04 x64, точное имя репозитория и отсутствие старой установки. Затем он:

- устанавливает пакеты Ubuntu `ca-certificates`, `git`, `docker.io` и `docker-buildx`, затем явно включает и запускает Docker;
- создаёт отдельного пользователя `skifrunner`;
- готовит приватный каталог `/opt/skif` и файл `/opt/skif/.env` с правами `0600`, не меняя существующий файл;
- получает метаданные последнего официального `actions/runner`, выбирает только архив Linux x64, сверяет SHA-256 из GitHub API и безопасно распаковывает архив;
- запускает поставляемый в проверенном архиве официальный [`bin/installdependencies.sh`](https://github.com/actions/runner/blob/main/src/Misc/layoutbin/installdependencies.sh);
- скрыто запрашивает временный токен регистрации, регистрирует runner с меткой `skif` и устанавливает его как службу.

Токен запрашивается до изменения хоста, не показывается при вводе, не попадает в аргументы процесса и не печатается в сообщениях об ошибках. Если Python предупреждает о видимом fallback-вводе, терминал закрывается или ввод прерывается, установка прекращается до изменений. Не вставляйте токен в команду, историю shell, `.env`, сообщение или issue.

Членство пользователя `skifrunner` в группе `docker` фактически даёт административный доступ к VM. Доступ к репозиторию и право менять workflow должны иметь только доверенные владельцы.

## Секреты приложения до первого deploy

Установка runner не настраивает приложение. На самой VM заполните `/opt/skif/.env`; секретные значения не должны попадать в GitHub, чат или вывод команд. Нужны:

- четыре разных, актуальных токена Telegram-ботов;
- числовой Telegram ID владельца;
- настройки и ключ API модели, которые ожидает приложение.

Finance-бот уже зарегистрирован как `@Skif_Gorshkova_Finance_bot`, а его старый токен отозван. Нужен новый актуальный токен этого бота. Остальные три бота и числовой ID владельца ещё не настроены.

Сначала, находясь в корне актуальной копии репозитория на VM, скопируйте шаблон **только если файл назначения пуст**. Команда сохраняет существующий непустой файл с секретами без изменений:

```bash
if sudo test -s /opt/skif/.env; then
  echo '/opt/skif/.env уже заполнен; шаблон не копируется'
else
  sudo install -o skifrunner -g skifrunner -m 600 .env.example /opt/skif/.env
fi
```

Затем откройте файл безопасным редактором:

```bash
sudoedit /opt/skif/.env
sudo chown skifrunner:skifrunner /opt/skif/.env
sudo chmod 600 /opt/skif/.env
```

Заполните в нём точные поля шаблона:

- `SKIF_OWNER_IDS` — числовой Telegram ID владельца;
- `TELEGRAM_LEGAL_TOKEN`, `TELEGRAM_DESIGN_TOKEN`, `TELEGRAM_FINANCE_TOKEN`, `TELEGRAM_STRATEGY_TOKEN` — четыре разных актуальных токена;
- `OPENAI_API_KEY` и доступный аккаунту `OPENAI_MODEL`;
- проверьте лимиты `SKIF_DAILY_AI_CALLS` и `SKIF_DESIGN_ATTEMPTS`; `SKIF_BLOG_CHANNEL` можно оставить пустым, чтобы публикация была отключена.

Заполните секреты **до первого успешного deploy**. Первоначальная загрузка ветки могла произойти, пока репозиторий был публичным; тогда deploy job получил статус **skipped** из-за защиты workflow. Смена видимости на Private, появление runner со статусом Online и заполнение `.env` сами по себе новый workflow не запускают. Когда выполнены все три условия, отправьте свежий commit в ветку `skif`: например, откройте в GitHub `README.md` именно в ветке `skif`, внесите безвредное уточнение и выберите **Commit changes** в `skif`. Этот новый push запускает первый deploy.

Если реальный deploy job уже запускался и завершился ошибкой предварительной проверки, после исправления причины откройте именно этот упавший job в GitHub Actions и выберите **Re-run jobs**. Не запускайте второй экземпляр через `docker compose`: workflow сам управляет единственным контейнером и volume `skif_runtime`.

Docker engine не требует входящих портов. Не открывайте порт Docker в firewall или в настройках облачной сети.

## Проверка после ручного запуска

Следующие команды выполняются владельцем на VM, а не в рабочем каталоге разработки:

```bash
sudo systemctl status 'actions.runner.*' --no-pager
sudo -u skifrunner docker version
sudo ls -ld /opt/skif /opt/actions-runner
sudo stat -c '%a %U:%G %n' /opt/skif/.env
```

Ожидаются запущенная служба runner, доступ `skifrunner` к Docker и режим `600` у `.env`. Наличие runner ещё не доказывает готовность приложения: успешный deploy возможен только после заполнения всех секретов.

Workflow и локальные проверки подтверждают готовность конфигурации GitHub CI. Реальное развёртывание подтверждается отдельно: runner должен появиться Online, а deploy из приватной ветки `skif` должен успешно завершиться на VM. Эта инструкция не утверждает, что такие серверные шаги уже выполнены.

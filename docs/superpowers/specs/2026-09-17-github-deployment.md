# СКИФ: GitHub и существующая виртуальная машина

Светлана одобрила 17.09.2026 поправку к схеме: повторно использовать существующий `jukovskayasv-alt/rastem_vmeste`, разместить СКИФ в корне отдельной production-ветки `skif` и сохранить существующие `main` и сайт без изменений. Репозиторий пока публичный, поэтому владелец сначала меняет видимость на Private и только затем устанавливает self-hosted runner. GitHub Actions и исполнитель используют уже созданную Ubuntu 24.04 VM; новые платные ресурсы не создаются. Доступ к серверу у ассистента отсутствует; установка на ВМ и регистрация исполнителя требуют действий владельца.

## Поток

Изменение кода → тесты на GitHub → задание исполнителю `skif` → сборка отдельного Docker-образа → проверка конфигурации и Telegram без polling → остановка старого контейнера → запуск нового → проверка готовности. При неуспехе запуска восстанавливается старый образ. Одновременно получает сообщения только один экземпляр программы.

## Границы

- Программа остаётся командой четырёх ботов. Не добавлять новые продукты, блог-публикации и платные API-вызовы в установку.
- Токены и данные владельца вводятся только на сервере, вне Git. Старый опубликованный Telegram-токен не используется.
- `.env` расположен в `/opt/skif/.env`, сохраняется при обновлении. `runtime` — постоянный Docker volume. Исходные справочные данные `data/` поставляются в образе; личные данные и результаты живут в runtime.
- Секреты и тексты сообщений не выводятся в GitHub Actions. Автоматический откат касается кода, не базы данных; перед изменением схемы БД требуется отдельный план совместимости.
- Workflow принимает production-код только из ветки `skif` точного приватного репозитория `jukovskayasv-alt/rastem_vmeste`; PR проверяются на GitHub, никогда не исполняются на production runner. Один deployment за раз, без прерывания предыдущего.
- Изменения приложения: `check` возвращает ненулевой код при пропущенных настройках; `probe` проверяет Telegram и webhook без getUpdates; `health` проверяет свежесть heartbeat конкретного выпуска и всех четырёх ролей. Это не проверка качества ответов модели.
- Предварительные проверки и сборка выполняются до остановки текущей версии. Ошибка подготовки сохраняет работающий контейнер. Непрошедшая первая установка не оставляет запущенный неисправный контейнер.
- Установка runner создаёт отдельного Linux-пользователя. Членство в docker даёт фактически административный доступ к этой ВМ: установка разрешается только на выделенном сервере проекта; это явно сообщается владельцу.
- Runner загружается только из официального `actions/runner`, проверяется SHA-256 из GitHub API. Регистрационный токен запрашивается скрытым вводом на ВМ, не записывается в пакет. Существующую регистрацию не заменять автоматически.
- Не заявлять подключение, пока runner не появился Online и нет успешного реального запуска. Локальные тесты и симуляция Docker не являются проверкой ВМ.

## Проверки

Поведенческие тесты обновления с заменой только внешнего Docker-движка: успешная смена, ошибка сборки, ошибка preflight, неготовая новая версия с восстановлением прежней, неуспех первого запуска, блокировка параллельного запуска. Health: просроченный heartbeat, чужой выпуск, недостающая роль. CLI: отсутствие настроек действительно даёт ненулевой exit status. Затем все существующие 47 тестов.
